# カスタムマップ: Discord最新仕様を踏まえたUX構成

確認日: 2026-10-25。Discord公式API・変更履歴、discord.py 2.7.1のドキュメント、PyPIの公開情報と配布wheelのソースを確認した。wheelはPyPIのSHA-256を検証して読み取った。UIの送信や実機操作試験は行っていない。

本書は [Discord UX設計](escape-discord-ux.md)の表示方式・Interaction実装の詳細である。マップ採用、検索の意味、保存・復旧・権限の規則は既存の設計を維持する。

Discord上の機能名は「カスタムマップ」に統一し、「通常サーバー」と区別する。画面タイトル・カード・状態表示はUX設計の命名規則に従う。

## 1. 推奨する構成

常設の「カスタムマップで遊ぶ」パネルを入口とし、各利用者には本人だけのホームを開く。新規のカスタムマップ用画面はComponents V2と `discord.ui.LayoutView` を使い、検索は選択式Modal、作品一覧は詳細ボタン付きのSectionで表示する。共有の準備・プレイカードと、本人用の検索・環境案内を分ける。

前案の「通常Embedを基本として新しい方式を必須にしない」方針を改訂する。使用中のdiscord.py 2.7.1で必要な機能に対応できるため、新規画面の標準をV2とする。既存Paper / Forgeの表示は別メッセージで維持し、互換表示は代替経路として提供する。

## 2. 確認した仕様と設計への適用

| 公式仕様・SDKの確認 | 採用する設計 |
| --- | --- |
| Components V2はContainer、Section、Text Display等を提供する。メッセージ内の総要素数上限は40である。 | 作品情報とその作品の詳細ボタンを隣接させる。原則5作品、要素数に余裕を残す。 |
| V2のメッセージでは従来のcontent / embedsを同居させられず、V2フラグを後から外せない。 | 新しい専用パネルを作成し、既存ステータスをそのままV2へ変換しない。 |
| Modalは1～5個のトップレベル要素を持てる。LabelでSelectやText Inputを包める。 | 人数・難易度・時間・キーワード・並び順を1つの検索フォームに置く。 |
| Radio Group、Checkbox Group、CheckboxはModal専用であり、Label内に置く。discord.pyでは2.7で追加された。 | 少数の選択肢はRadio Group、準備項目の自己申告はCheckbox Groupを使う。共有メッセージにチェックボックスを直置きしない。 |
| サブコマンドがある場合、グループ名だけのコマンドは実行できない。 | 実行可能な入口を `/escape home` とし、裸の `/escape` をホーム表示コマンドとして定義しない。 |
| Select / autocompleteの候補数は25までである。 | 作品全件の固定choicesを使わず、作品名検索・ページ送り・動的候補を使う。 |
| LayoutViewの表示テキストは全体で4000文字までである。 | 作品名と条件を短く表示し、長い導入説明・作者の原文は詳細に分ける。 |
| 通常の応答期限は3秒、Interactionトークンは15分である。LayoutViewの既定timeoutは180秒であり、ephemeralでtimeout=Noneを渡した場合は900秒に補正される。 | 個人画面はtimeout=900を明示し、DB上の画面期限も作成から15分とする。永続ジョブと共有カードは分離し、期限切れの個人画面はホームから復帰する。 |

根拠: [Components Reference](https://docs.discord.com/developers/components/reference)、[V2メッセージの利用](https://docs.discord.com/developers/components/using-message-components)、[Interaction仕様](https://docs.discord.com/developers/interactions/receiving-and-responding)、[Application Commands](https://docs.discord.com/developers/interactions/application-commands)、[discord.py 2.7.1 API](https://discordpy.readthedocs.io/en/v2.7.1/interactions/api.html)、[discord.py変更履歴](https://discordpy.readthedocs.io/en/stable/whats_new.html)。

調査時の[PyPI最新安定版](https://pypi.org/project/discord.py/)も2.7.1であり、リポジトリの固定版と一致した。今回の構成のために依存更新や別のDiscordライブラリを導入する必要はない。

## 3. 常設入口・本人用画面・共有カード

### 常設入口

許可済みチャンネルに1枚の「カスタムマップで遊ぶ」パネルを置く。「ホームを開く」「マップを探す」「続きから」の3ボタンと、匿名の空き枠情報だけを載せる。押した人の私的な検索や履歴で共有パネルを書き換えない。

- 「ホームを開く」: 本人だけのホームを表示する。
- 「マップを探す」: 直ちに検索Modalを開く。ホーム経由を必須にしない。
- 「続きから」: 本人が閲覧できる中断データを一覧表示する。

パネルは `timeout=None` と安定したcustom_idで登録し、Bot再起動後にDBのMessageBindingから再登録する。導入・移設は管理者の明示操作で行い、各コマンド呼び出しで新しい共通パネルを増やさない。パネルが見つからない場合も `/escape home` から操作できる。

### 本人用画面

検索・ホーム・個別の環境準備はephemeralで表示する。ページ切り替え・詳細・戻るは可能な範囲で同じ画面を更新する。期限切れ時は `/escape home` の「前回の条件で探す」で新しい画面を作る。

### 共有カード

準備ルームとプレイの状態は同じ代表カードを段階的に更新する。各参加者には「自分の準備」、代表者には「開始・保存中断・終了」、それ以外には許可された操作だけを返す。共有ボタンを押した人の権限を毎回確認する。ボタンを表示できないことだけを権限制御にしない。

本人に関係のない参加者の設定フォームを表示しない。全員向けカードには人数と開始条件、本人向けカードには自分のOS・ID承認・準備の不足を表示する。マップ名等の公開範囲の規則は既存UX設計に従う。

## 4. 検索は1つのフォーム、結果は作品ごとのボタン

### 基本検索Modal

フォームを開くだけでは条件を変更しない。現在値を初期値にし、送信時に一括適用する。キャンセルした場合は元の検索を維持する。

| Label | 子コンポーネント | 内容 |
| --- | --- | --- |
| 遊ぶ人数 | String Select | 指定なし、2～16人の選択肢。コマンド等で範囲外の現在値がある場合は「現在: 17人」等の一時候補を追加し、フォームを開くだけで条件を変えない。候補数は25以内とする。 |
| 謎解き難易度 | String Select | 指定なし、入門、やさしいまで、標準まで、難しいまで。最高段階まで含める場合は指定なしとする。 |
| 所要時間の目安 | String Select | 指定なし、30 / 60 / 90 / 120 / 180 / 240分以内。任意上限は詳細条件から指定する。 |
| キーワード | 任意Text Input | 作品名・作者名。空欄可。 |
| 並び順 | String Select | 人気、時間、難易度、対応人数、自分の直近プレイ等。現在の共有先の履歴を表示できる場合だけグループ順を加える。 |

5つのLabelで完結し、普段使う3条件を変えるたびに別画面を往復しない。選択肢を減らす場合でも検索サービスは任意人数・分数を扱い、コマンドとの意味を揃える。

### 詳細条件Modal

基本検索の内容を維持して、追加条件だけ変更する。トップレベルは次の5つとする。

1. 配布元: Select。
2. パックの準備: Radio Groupで「指定なし / パックなし / 指定パックあり」。
3. 自分のプレイ状況: Select。
4. 任意の時間上限: Text Input、整数の分数。基本フォームと同じ単一の `max_minutes` を編集し、空欄なら時間上限なしとする。
5. 追加条件: Checkbox Groupで「難易度未記載を含める」「時間未記載を含める」「ホラーなし」「アスレチックなし」「戦闘なし」。未選択も有効でありrequired=falseとする。

時間の下限と上限を自由記述の範囲記号で入力する方式は、初期UIには採用しない。利用者が求める「この時間以内の目安」に集中し、入力の説明とエラーを減らす。基本Selectには現在の任意分数も1候補として追加し、すべての画面が同じ `max_minutes` を更新する。プリセットと任意値を別々に保持しない。0件画面の「時間上限を外す」は `max_minutes=null` とし、以前の値を復活させない。詳細条件の解除はその対象を示し、全条件のリセットとは区別する。

### 結果カード

作品ごとに `Section(TextDisplay, accessory=Button)` を使う。上部に条件と件数、下部に条件変更・詳細条件・環境条件・条件リセット・ページ移動を置く。作品選択のための追加Selectは不要である。

「環境条件」は結果画面から別Modalを開き、Minecraft版を選択する。詳細Modalへ6個目のLabelを足さず、Modal送信後に次のModalを直接開かない。候補は公開カタログに存在する版と指定なしであり、現在値を保持する。25候補を超える場合はメッセージ上の候補検索・ページ分割を使い、1つのSelectへ全件を詰めない。通常の利用者には版指定を要求しない。

```text
カスタムマップを探す
4人 / 標準まで / 120分以内 / 短い順  3件
カスタムマップ枠に空きあり（開始時に再確認）

作品A  2～4人 / 標準 / 作者目安60～90分 / パックなし    [Aの詳細]
作品B  2～6人 / やさしい / 作者目安90～120分 / 指定パック [Bの詳細]
作品C  2～4人 / 標準 / 作者目安120分 / 自分は中断中      [Cの詳細]

[条件変更] [詳細条件] [並び順]
[環境条件] [条件リセット]
[前へ] [次へ] [ホーム]
```

仮データによる説明図である。通常は5作品、文字量が多い場合は3作品表示に切り替えられる。モバイルかどうかをBotが自動検出できると仮定せず、表示件数は利用者の表示設定で選べる。タイトルの切り詰めが必要でも詳細で全文を確認できる。色だけで状態を区別しない。

構成例はContainer 1、見出しTextDisplay 1、Separator 1、5 Sectionと各TextDisplay・Buttonで15、操作ActionRowと3 Buttonで4、環境・リセットActionRowと2 Buttonで3、移動ActionRowと3 Buttonで4、補足TextDisplay 1の合計30要素である。上限40まで詰めず、表示全体4000文字以下を生成時に検証する。3件表示は同じ構造で24要素となる。ボタンを1行に詰めず、操作群を分ける。

## 5. 詳細・準備・履歴は次の操作を優先する

### 作品詳細

最初に人数・謎解き難易度・時間目安・クライアント準備の負担を表示する。主操作は「このマップで準備」。自分の中断データがあれば「続きから」を優先し、新規作成は補助操作とする。作者原文や技術的な条件は別の詳細表示へ送る。

「このマップで準備」は本人用の作成Modalを開く。Labelはプレイ名、予定人数、共有先の3つである。共有先は現在のチャンネルを初期値にし、必要な場合だけChannel Selectで変更する。選択できても承認済み共有先と閲覧範囲の検査は省略しない。

### 参加者の準備

共有カードの「参加する」から登録できる。承認済みUUIDと同じクライアント要件の準備記録があれば、同じ質問を繰り返さない。不足があれば本人用の準備案内を開く。

OSは既知の設定を再利用し、初回はRadio GroupでWindows / macOS / Linuxを選ぶ。準備状況のModalは、OS、必要な準備項目のCheckbox Group、未登録時だけMinecraft名のText Inputで最大3 Labelとする。チェックは自己申告として保存し、全項目未完了でも状況を保存できる。全部満たした場合だけ「準備できた」と表示する。ID承認状態は別に扱う。

案内本文のLink Buttonは「公式Launcher」「今回のパック」「作者の説明」等、目的別の短いラベルにする。リンクをクリックした事実や、その先のダウンロード完了は取得できると仮定しない。準備済みはフォームによる自己申告である。パック不要ならパック関連のリンクと確認項目を出さない。

接続先は本人が選択・コピーできるコード形式の文字列で表示する。Discord BotからOSクリップボードへ書き込む「コピー」ボタンや、Minecraftを自動起動する独自リンクを前提にしない。

### 履歴

直近履歴の最初のページは操作しやすい5件とし、保存データがある中断・プレイ中の回を先に案内できる。各行に現在の状態に適したボタンを付け、中断なら再開準備、稼働中なら接続案内、完了・消去済みなら新規作成とする。記録を大量に読む場合は1ページ10件の表示も選べる。クリアと削除の意味は従来設計どおり分離する。

## 6. Interactionと永続化の実装規則

- 検索フォーム等を開くボタンには3秒以内にModalで直接応答する。先にdeferしてから同じInteractionでModalを開く設計にしない。
- Modal送信後に別Modalを直接開かない。結果・入力エラー・次の操作をメッセージで返し、必要ならそのボタンからフォームを再表示する。誤入力時の値は保持する。
- フォームからの初回検索、共有パネル・共有カードを起点とした個人用応答は、`defer(ephemeral=True, thinking=True)` でtype 5の本人用応答を確保してから `edit_original_response(view=...)` で返す。`thinking=False` の既定値に依存しない。
- type 6 / 7による元メッセージ更新は、所有者・メッセージID・画面世代を照合した本人用画面だけに限定する。軽いページ送りはUPDATE_MESSAGE、重い更新はDEFERRED_UPDATE_MESSAGE後の編集とする。共有メッセージを起点とするModal送信にtype 6を使って個人結果を描画しない。
- type 5のdefer時はephemeralだけを設定し、V2コンポーネントはedit original responseで設定する。初回deferにV2フラグを無理に含めない。
- 初期化・起動はジョブIDを確定してすぐ応答し、共有カードの更新はBot認証で行う。15分のInteractionトークンを使い続けない。
- Interactionトークンの有効期限、LayoutViewの無操作timeout、DBの画面期限、保存した検索条件の寿命を区別する。個人画面はtimeout=900と作成から15分のDB期限を明示し、検索条件は画面期限後もホームから再利用できるように保持する。Modal入力中に元の画面が期限切れになっても、現在の権限を再確認した新しい本人用応答へ値を引き継ぐ。
- 共有メッセージを参加操作で編集する処理と、押した人へephemeralを返す処理を分ける。投稿先が共有カードだからといって個人のID申請や準備設定を共有本文へ返さない。
- 共有カードの更新はセッション単位でまとめ、状態変化は速やかに、同時多数の準備更新は短時間に集約する。Discordの429とretry_afterを尊重し、固定頻度の連続投稿で通知を増やさない。
- `MessageBinding` にrender_modeとrenderer_revisionを持たせる。V2フラグを外すロールバックを行わず、代替の新規メッセージを作成して関連付けを切り替える。
- 互換表示は `/escape home simple:true` から利用できる。新規のLegacy Embed画面を返し、同じサービス・権限・状態規則を使う。InteractionからDiscordクライアントの版や端末OSを推測して切り替えない。

応答順序の根拠は [Interaction Callback Types](https://docs.discord.com/developers/interactions/receiving-and-responding#interaction-response-object-interaction-callback-type)である。`MODAL_SUBMIT` に対するModal応答と、既に応答したInteractionへの2回目の初期応答を前提にしない。

## 7. 採用しない構成

- 外部WebダッシュボードやDiscord Activityは初期に追加しない。今回の検索・準備・状態表示はネイティブのコンポーネントで扱える。
- User Install、DM、Group DMを起動権限の経路として追加しない。サーバー運用は許可guild内のGuild Installと現在の権限に閉じる。
- 全作品をautocompleteだけに載せたり、検索条件ごとに共有チャンネルへ新しいメッセージを投稿したりしない。
- 新しいファイルアップロード機能があっても、利用者にマップやパックのアップロードを要求しない。クライアント準備は作者リンクと案内で行う。

## 8. 受入確認の追加

1. `/escape home`、常設パネル、短縮コマンドの各経路から同じ機能を利用でき、裸の `/escape` を実行可能と案内しない。
2. 主要5項目が1つのModalで設定でき、キャンセルでは条件を失わず、難易度・時間の条件が検索サービスと一致する。
3. 詳細条件で任意時間上限を設定・解除した結果が、基本検索と結果ヘッダーにも正しく反映される。120→任意150→空欄の結果は上限なしであり、120が復活しない。17人等の範囲外現在値も、フォームを開いて保存するだけでは失われない。
4. Modalは最大5 Label、Radio / CheckboxはModal内のみ、Select候補は25以内、V2総数は40以内、テキストは4000文字以内である。
5. Windows / macOS / LinuxのDesktopとiOS / AndroidのDiscordで、5件・3件表示、長い作品名、フォームのスクロール、日本語入力、戻る操作を確認する。未実施の端末試験を対応済みとはしない。
6. 共有カードを複数人が操作しても、各自の準備・ID申請は本人用に返り、共有状態の更新競合で古い情報に戻らない。
7. パネルと準備カードはBot再起動後も動き、ephemeralの期限切れはホームから回復できる。
8. V2に従来embedを混ぜず、互換表示への切替は別メッセージで成立する。
9. 長時間ジョブがトークン期限を超えても、共有カード・セッション一覧から状態を確認できる。429で更新が遅れても二重初期化しない。
10. Link Buttonを押しただけで準備OKやダウンロード済みにしない。コピー・自動起動など未提供のクライアント機能を案内しない。
11. 共有パネルから検索Modalを送信しても、type 5の本人用結果だけが作成され、共有パネルはそのまま残る。共有更新を伴う参加操作でも、個人結果と共有状態の書込先を区別する。
12. Minecraft版の絞り込みを環境条件から変更・解除でき、0件画面や結果ヘッダーにも版条件を表示する。候補が多い場合も25上限を守る。

## 9. 改訂後のレビュー

前回の独立レビューは前回版に対するものである。今回のV2・フォーム・コマンド入口の改訂も、SDKとInteraction制約、利用者の動線を2つのサブエージェントが独立確認した。追加5件を修正し、修正後の再確認でも重大な未解消事項は見つからなかった。結果は [レビュー記録](escape-design-review.md)に追記した。実装前の設計確認であり、API送信・端末試験の代替ではない。
